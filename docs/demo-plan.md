# D08 — план защиты текущего backend

Подготовил Дмитрий. Это предварительный план: регламент не получен, репетиции и замеры времени выступления не проводились. Frontend — заглушка; полный клиентско-банковский сценарий показывать как реализованный нельзя.

## Порядок рассказа

1. Проблема: подготовка заявки и рассмотрение досье; H01–H04 — гипотезы из [исследования](research.md), а не доказанные боли и экономия.
2. Решение: два кабинета в целевом [MVP](product.md), сохранённая заявка, локальные симуляторы и объяснимая рекомендация; отделить целевой объём от имеющегося backend.
3. Демонстрация доступного API: readiness, демосессия, каталог; затем существующий PostgreSQL integration-тест создания/submit и worker до MANUAL_REVIEW. Назвать тест интеграционным тестом, а не веб-E2E или полным E01.
4. Объяснение: показать policy-v1 и существующий golden case меньшей суммы; candidate — не подтверждённое предложение банка, score — не вероятность одобрения.
5. Надёжность: показать фактический результат тестов и перечислить, что они покрывают. Таймаут — техническая ветка, не кредитный отказ. Наличие lease не выдавать за проверку всех сценариев аварийного восстановления.
6. Ограничения: нет рабочих кабинетов и полного решения/принятия/завершения; источники синтетические; подпись и выдача только планируемые имитации. Следующий шаг — B06/B07, frontend, независимая QA-приёмка.

## Подготовка показа

Запуск и команды — [backend-development.md](backend-development.md). Проверить их на выбранном окружении перед выступлением; использовать свежую выделенную БД для тестов. Открыть [матрицу покрытия](requirements.md) и не приписывать тестам непроверенные гарантии. Не показывать секреты, cookie, токены, env dump и реальные документы. Если сервис недоступен, назвать сбой; сохранённый результат теста обозначить как запись предыдущего запуска.

Для текущего API достаточно локально выполнить запросы health/ready, demo/profiles, demo/session и products с cookie через HTTP-клиент. Не публиковать loopback-ссылки как доступный зрителю стенд. Создание и обработку заявки демонстрировать по имеющемуся тесту worker в выделенной БД; он вызывает worker в процессе теста и не доказывает работу отдельного worker-процесса. Проверка отдельного процесса была выполнена при onboarding, повторять её нужно отдельно при таком заявлении.

## Ответы без завышенных обещаний

- Почему без LLM: основной результат обеспечивает проверяемая учебная policy; для основного пути LLM не требуется.
- Почему сотрудник: в P0 он подтверждает финальные условия/отказ; сам ручной шаг не гарантирует безопасность.
- Каков эффект: эксперимент D07 ещё не проведён, экономия не доказана.
- Готов ли банк использовать: нет, это учебный прототип с синтетическими данными и ограничениями, не production-система.

До завершения D08: получить регламент, дождаться полного E01, проверить технические утверждения с владельцами, провести репетицию и записать длительность/сбои. Длительность доклада сейчас не выдумывается.
