# 12 Инструкция Рамазану

### Блок 1 Тест план

**Q01 Матрица приёмки.** Связать R01–R18 с E01–E16 ниже и конкретными файлами. Разделить smoke, E2E, API, security и recovery. Заранее подготовить тест-кейсы, пока разработчики пишут код, а не ждать финала.

**Q02 Независимые ожидания.** С Димой подтвердить ожидаемые пользовательские результаты, с Ильёй независимо пересчитать golden cases. Нельзя строить expected путём вызова той же тестируемой функции. Для каждого бага — шаги, профиль, исходные данные, ожидаемое/фактическое, request_id, серьёзность.

### Блок 2 Проверка продукта

| ID | Проверка | Ожидаемый результат |
|---|---|---|
| E01 | Пустая заявка → проверки → сотрудник → предложение → принятие → подписание → выдача | Все шаги серверные, данные и история сохранены, выдача явно симулирована |
| E02 | Исходная сумма не проходит, меньшая проходит | Альтернативная сумма обоснована; клиент соглашается сам |
| E03 | Недостающее или противоречивое поле | NEEDS_INFO, конкретное уточнение; после исправления новая revision и повторный расчёт |
| E04 | Просрочка 35 дней в синтетическом БКИ | Отрицательная рекомендация, сотрудник фиксирует отказ; клиент видит корректную причину |
| E05 | Клиент отклоняет предложение | DECLINED_BY_CLIENT, нет подписания и выдачи |
| E06 | Timeout БКИ | Retry, затем PROCESSING_ERROR; никакого кредитного отказа и фиктивного score |
| E07 | Клиент A запрашивает заявку/документ B, client вызывает bank endpoint | Нет доступа; данные не раскрываются ни в списках, ни по прямому ID |

| E09 | Двойной submit/accept/sign, два сотрудника одновременно | Один эффект; повтор с тем же ключом возвращает результат, устаревшая версия — 409 |
| E10 | Старый worker завершился после новой ревизии | Старый результат не меняет актуальное состояние |
| E11 | Отрицательная сумма, нулевой срок, лишние поля, файл неверного типа/размера | Понятная валидация; статус и БД не повреждены |
| E12 | После сборки блокированы внешние запросы | Основной сценарий работает; не нужны облачные ключи и платные сервисы |
| E13 | Смена демопользователя в том же браузере | Сессия и кэш заменены, данные предыдущего клиента не видны |
| E14 | Предложение и документ старой ревизии | Принятие/подписание отвергнуто, пользователь получает актуальные данные |
| E15 | Ширины 1440/768/390 и клавиатура | Основные кнопки доступны, нет потери полей и перекрытий |
| E16 | Чистый clone, README, Compose, seed повторно | Один понятный запуск; повторный seed не удаляет созданные данные |

**Q03 Автоматизация.** API/integration tests используют PostgreSQL. E2E — отдельные browser contexts для клиента и сотрудника, чтобы одна cookie не перезаписывала другую. Проверять UI и итог в API/БД, а не только появление текста. Ожидания по состоянию, не фиксированные sleeps. Сброс данных только в выделенной тестовой БД.

**Q04 Проверка безопасности и сбоев.** Пройти прямые URL документов, IDOR, CSRF на изменяющих запросах, выключенный DEMO_MODE, неверную роль, чужую компанию, скрытые поля. Искусственно остановить worker после claim и перед commit, дождаться восстановления. Не проводить реальные атаки на сторонние сервисы.

### Блок 3 Релизная приёмка

**Q05 Чистый запуск.** Повторить README на отдельном окружении или чистом Docker project. Записать ОС, архитектуру CPU, RAM, версии Docker/Compose, время первого старта и повторного старта. Указать, требуется ли сеть для загрузки образов/пакетов. Основной runtime после сборки должен работать автономно.

**Q06 Комплект сдачи.** Проверить архитектурную схему, модель данных, состояния, OpenAPI, API-описание, коллекцию, тест-кейсы, README, THIRD_PARTY_NOTICES, синтетические данные и доступы. Коллекция не содержит персональных токенов; параметры и CSRF/session flow воспроизводимы.

**Q07 Отчёт о готовности.** Blocker: не запускается, теряет данные, обходит права, дублирует выдачу, нет полного пути. Critical: неверное решение на эталоне, не работает уточнение/отказ, stale run меняет заявку. Перед сдачей открытых blocker/critical быть не должно. Остальные дефекты описываются; не скрывать их скриншотами.

**Готовность роли:** тест-план, коллекция запросов, автоматизированный smoke и ключевые E2E, проверенный чистый запуск, отчёт с фактическими pass/fail и известными ограничениями. QA подтверждает качество; владельцы кода исправляют найденные ошибки.

**Стартовый запрос ИИ:** «Ты QA-инженер. Прочитай AGENTS.md, матрицу R01–R18 и E01–E16. Реализуй Qxx и проверки, не меняя бизнес-логику ради зелёного теста. Ожидания выводи из спецификации независимо от реализации. При дефекте верни минимальное воспроизведение и логи без секретов. Не называй непроведённую проверку успешной».

Перед началом прочитать ../../../AGENTS.md, общие разделы ../01-team-instructions.md и ../02-architecture.md. Эта выдержка не заменяет общие контракты.
