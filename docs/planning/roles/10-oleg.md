# 10 Инструкция Олегу

### Блок 1 Архитектура и данные

**B01 Каркас.** Создать модульный backend, web frontend, PostgreSQL и отдельный worker на том же backend-образе. Выбрать и зафиксировать точные проверенные версии после первой успешной сборки; не ставить `latest`. В `docs/adr/001-modular-monolith.md` объяснить выбор и ограничения. Не создавать отдельный сетевой сервис для чистой функции скоринга.

**B02 Контракты и БД.** Реализовать сущности и ограничения из архитектуры, миграцию начальной схемы, схемы Pydantic и OpenAPI v1. Утвердить вход/выход risk-модуля с Ильёй и примеры ответов с Игорем. Генерируемые API-типы фиксировать вместе с контрактом.

**B03 Сессии и доступ.** Демо-вход выбирает только заранее созданного пользователя на сервере. Роль берётся из БД; все операции проверяют и роль, и связь с компанией. Разделить клиентские и банковские response-схемы. Для работы без demo mode предусмотреть документированный вход тестовых пользователей с хешированными паролями, без self-service регистрации и внешних рассылок.

### Блок 2 API и кредитный конвейер

**B04 Черновик и отправка.** CRUD только в разрешённых состояниях. Submit проверяет обязательность данных, фиксирует неизменяемую ревизию и атомарно создаёт job. Idempotency-Key предотвращает повторную отправку; optimistic version защищает от устаревших действий. Сохранять audit event в той же транзакции, что и изменение статуса.

**B05 Worker.** Claim job с lease, проверки локальных источников, feature builder, вызов Ильиного `evaluate`, сохранение результатов и переход в нужный статус. Сетевые/технические ошибки отделить от бизнес-результатов. Повторный запуск job не должен создать второе решение или второе предложение. Устаревшая ревизия не должна перезаписать новую.

**B06 Уточнение и решение.** Запрос сотрудника фиксирует список полей/документов и текст. Клиент передаёт дополнения, сервер создаёт следующую ревизию, старые результаты остаются в истории. Подтверждение сотрудника ссылается на действующий run и candidate offer. Отказ фиксирует причину. Нельзя произвольно PATCH-ить статус.

**B07 Принятие и имитация.** Принятие предложения блокирует его условия, создаёт неизменяемую версию документа. Подписание фиксирует согласие с конкретным hash документа, затем persistent job имитирует выдачу. Одна заявка — максимум одна запись simulated disbursement. Повтор после timeout возвращает тот же результат.

### Блок 3 Инфраструктура и сборка

**B08 Запуск.** Compose со сборкой web/api/worker, PostgreSQL и одноразовым init для миграций и seed. Web публикуется на `127.0.0.1:8080` по умолчанию; БД наружу не публикуется. Один и тот же origin для UI и API. Volumes сохраняют БД и документы. Seed идемпотентен и не сбрасывает созданные заявки.

**B09 Надёжность и конфигурация.** Health/readiness endpoints, bounded retries, lease reclaim, структурированные логи с request_id и application_id без содержимого документов и токенов. `DEMO_MODE` управляет входом и тестовыми профилями; production-профиль не должен молча использовать demo credentials. Для публичного demo стенда явно признать отсутствие пользовательской приватности и использовать только синтетические данные.

**B10 CI и релиз.** Backend lint/tests, frontend typecheck/build/tests, проверка OpenAPI, затем интеграционные и E2E проверки. Образы зафиксированы по проверенным версиям/дижестам; lock-файлы коммитятся. Перед дедлайном tag и commit hash, доступ жюри и архив артефактов; не переписывать сданный тег.

**B11 Техническая документация.** Обновить `architecture.md`, ER-диаграмму, state machine, `api.md`, OpenAPI, запуск и troubleshooting. Проверить сборку на x86_64 и arm64, если это реально доступно; при отсутствии второго окружения честно указать, что проверена только одна архитектура. Не заявлять production-ready и соответствие банковским регуляторным требованиям.

**Готовность роли:** весь P0 работает после чистого запуска, миграции и seed идемпотентны, данные переживают перезапуск, повторные запросы не дублируют действия, контракты совпадают с документацией.

**Стартовый запрос ИИ:** «Ты backend-разработчик и архитектор. Прочитай AGENTS.md и 02-architecture.md. Реализуй Bxx небольшим PR, сохраняя state machine и контракт risk-v1. Добавь транзакции, проверки владельца, версию и идемпотентность там, где они требуются. Не реализуй кредитные правила второй раз вне risk. Проверь интеграцию с PostgreSQL, а не только SQLite. Отдельно укажи непроверенные окружения».
