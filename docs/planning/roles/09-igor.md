# 9 Инструкция Игорю

### Блок 1 Клиентский кабинет

**F01 Вход и главная.** Экран `/demo` содержит понятные карточки синтетических клиентов и сотрудника, кнопку «Начать новую заявку» и предупреждение о демонстрационном режиме. Кнопка вызывает серверную выдачу сессии. Главная показывает текущую компанию, черновики/заявки и следующий шаг. Тестовые заявки в отдельном разделе, они не заменяют чистую форму.

**F02 Создание заявки.** Маршрут `/applications/new`: выбор цели и продукта, сумма, срок, сведения о компании, финансовые показатели, документы и итоговая проверка. Поля и границы брать из API продукта. Сохранение черновика явное; индикатор показывает время успешного серверного сохранения, а не только local state. Автосохранение — P1. При уходе с несохранёнными правками предупредить.

**F03 Карточка заявки.** `/applications/:id`: статус, история, ожидаемый следующий шаг, время последнего обновления, запрошенные уточнения, результат и условия. Polling каждые 2 секунды только в активных состояниях; остановка в терминальных и при скрытой вкладке. При восстановлении вкладки запросить данные заново. Не показывать искусственную шкалу процентов готовности.

**F04 Предложение и завершение.** Клиент видит сумму, срок, ставку, ежемесячный платёж, суммарную выплату, отсутствие комиссий в демонстрационной модели и причину изменения суммы. Кнопки «Принять условия» и «Отклонить предложение». После принятия — документ для ознакомления и явная кнопка «Смоделировать подписание». На итоговом экране «Выдача смоделирована. Реальные средства не переводились».

### Блок 2 Банковский кабинет

**F05 Очередь.** `/bank/applications`: статусы, дата, сумма, продукт, компания, необходимость действия и время ожидания. Сортировка и фильтры на сервере. Пустое состояние объясняет, что заявок нет. Не загружать на frontend все данные всех клиентов ради фильтрации.

**F06 Досье.** `/bank/applications/:id`: заявленные данные и источники проверок, статус каждого источника, оценка риска, факторные вклады, расчёт доступности, рекомендованные условия, история ревизий. Сотрудник видит, какие сведения заявлены клиентом и какие получены от симулятора. Изменённое имя файла не считается проверкой его содержания.

**F07 Действия.** Отдельные кнопки: запросить уточнение, подтвердить рассчитанное предложение, отказать с причиной. Подтверждение доступно только для действующей рекомендации. В P0 нельзя свободно вписать любую сумму и ставку. При 409 обновить карточку и показать, что данные изменились; не повторять автоматически опасную операцию с новой версией.

### Блок 3 UX и API интеграция

**F08 Единые компоненты.** Поля с подписями, денежный ввод, ошибки рядом с полями, статус, timeline, подтверждение действий и документ. Доступность с клавиатуры, заметный focus, читаемые контрасты. Ошибка не должна обозначаться только цветом. Рабочие ширины проверки: 1440, 768 и 390 px; это наши тестовые размеры, не требование кейса.

**F09 API-клиент.** Генерируемые типы из OpenAPI либо единый строго типизированный слой, согласованный с Олегом. Cookie-сессия, CSRF-токен для изменений, обработка 401/403/404/409/422/503. При переключении демопользователя очищать кэш запросов и форму, отменять незавершённые запросы; иначе возможна утечка данных предыдущего профиля в UI.

**F10 Проверки.** Unit/component-тесты полей и действий, сборка и typecheck. С Рамазаном E2E по новой заявке, уточнению, отказу и смене пользователя. Полный показ не должен зависеть от frontend mocks. Состояния loading, empty, error и success реализуются для каждого основного экрана.

**Граница роли:** не вычислять итоговый скоринг, ставку, месячный платёж и разрешения самостоятельно. Допустимо локально форматировать полученные суммы и проверять заполнение полей; сервер повторяет валидацию. Клиентский код по природе доступен браузеру — безопасность не строится на его сокрытии.

**Готовность роли:** оба кабинета работают с реальным API, чистая форма проходит E01, разрешения не имитируются CSS, корректны мобильная ширина и ошибки, нет заглушек с заранее одобренным результатом.

**Стартовый запрос ИИ:** «Ты frontend-разработчик. Прочитай AGENTS.md и 02-architecture.md. Реализуй Fxx в frontend по контракту v1. Не меняй backend, статусы и кредитные формулы. Предусмотри loading, empty, error, 409 и очистку кэша при смене сессии. Выполни typecheck, сборку и релевантные тесты. Перечисли реальные результаты и оставшиеся интеграционные зависимости».

Перед началом прочитать ../../../AGENTS.md, общие разделы ../01-team-instructions.md и ../02-architecture.md. Эта выдержка не заменяет общие контракты.
