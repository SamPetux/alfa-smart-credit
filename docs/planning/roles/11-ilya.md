# 11 Инструкция Илье Кудрявцеву

### Блок 1 Признаки и источники

**S01 Словарь данных.** Для каждого поля определить смысл, единицу, период, допустимый диапазон, источник и значение missing. Выручка, операционные расходы и существующие платежи — среднемесячные; расходы исключают кредитные платежи, чтобы избежать двойного вычитания. Существующая долговая нагрузка берётся из симулятора БКИ; заявленные клиентом данные сравниваются с ней по явному правилу.

**S02 Контракт источников.** Подготовить JSON fixtures реестра и БКИ: active/inactive, возраст бизнеса, платежи и просрочки, observed_at, scenario_id, `is_synthetic=true`. Технические состояния success/timeout/unavailable/schema_error не смешивать с фактами о компании. Илья владеет содержимым fixtures, Олег — их загрузкой и отказоустойчивым вызовом.

**S03 Feature builder.** Чистая функция из заявленных данных и результатов источников в `RiskInput`. Отдельные признаки происхождения, расхождения и полноты. Не подменять missing нулём, не использовать email/имя/fixture ID для кредитного решения. Не оценивать реальную платёжеспособность по наличию произвольного загруженного файла.

### Блок 2 Скоринг и кредитная политика

**S04 Score.** Реализовать прозрачную балльную модель из архитектуры, включая границы интервалов. Возвращать общий балл, risk_band и вклад каждого фактора. Это эвристический рейтинг для прототипа; он не является вероятностью дефолта или одобрения.

**S05 Policy.** Отдельно реализовать ограничения продукта, стоп-факторы, расчёт DSCR и платежа, решение по данным и поиск альтернативной суммы. Порядок правил фиксирован. Все финальные рекомендации в MVP идут сотруднику, за исключением запроса недостающих сведений и технической ошибки. Backend управляет статусами; функция не пишет в БД.

**S06 Версионирование.** `policy_version` и `model_version` присутствуют в каждом результате. Обновление правил не меняет прошлый результат без нового evaluation run. Одни и те же входные данные и версия должны давать один и тот же результат.

### Блок 3 Объяснения и эталонные сценарии

**S07 Причины.** Машинные reason_codes стабильны; тексты клиента и сотрудника различаются. Клиент получает понятные причины и действия; сотрудник — входные значения, пороги и расчёт. Текст не обещает одобрение после «улучшения показателя». UI не должен показывать процент вероятности, которого нет в модели.

**S08 Golden cases.** Подготовить fixtures и ожидаемые результаты для: обычного предложения, меньшей суммы, уточнения, отказа по просрочке, отказа по недоступности минимальной суммы, timeout источника и конфликтующих данных. Эталонные результаты независимо пересчитать и проверить с Рамазаном.

**S09 Тесты.** Unit-тесты порогов и Decimal-расчётов; свойства: при неизменных остальных признаках рост суммы не уменьшает платёж, рост существующих платежей не улучшает доступность, missing не повышает рейтинг, итог не выходит за ограничения продукта. Тесты на синтетике подтверждают правильность реализации правил, а не предсказательную силу модели.

**Готовность роли:** модуль `risk/` вызывается без сети и БД, контракт стабилен, policy описана, golden cases воспроизводятся, причины понятны, нет импортов FastAPI или ORM в чистой кредитной логике.

**Стартовый запрос ИИ:** «Ты разработчик демонстрационной кредитной логики. Прочитай AGENTS.md и разделы risk-v1 и policy-v1 в 02-architecture.md. Реализуй Sxx как чистые Python-функции с Decimal. Не выдумывай правила Альфа-Банка, ML-метрики, вероятность одобрения и внешние данные. Не меняй API и статусы. Добавь независимые граничные примеры и объяснение расчётов».
