# Правила работы ИИ агента над кредитным кабинетом

Общие инструкции для агентов в репозитории `alfa-smart-credit`. Источник базовых правил — пакет проектирования в `docs/planning/`; при расхождении с кодом Олег фиксирует решение в ADR.

## Перед задачей

1. Прочитать текущее состояние репозитория, README и вложенные инструкции. Затем прочитать `docs/planning/01-team-instructions.md`, `docs/planning/02-architecture.md` и инструкцию своей роли из `docs/planning/roles/`.
2. Получить конкретный ID задачи D/F/B/S/Q и критерии приёмки. Не реализовывать весь проект самостоятельно по одной фразе «сделай свою роль».
3. Проверить зависимости: API v1, risk-v1, policy-v1, enum статусов. Если их ещё не приняли на G0, подготовить контракт для согласования, а не создавать несовместимую собственную версию. Канон контрактов — `contracts/`.
4. Назвать изменяемые файлы, план проверки и предполагаемые ограничения. Выбрать маленький вертикальный результат, пригодный для PR.

## Владение

- Дима: требования, продуктовая документация, презентация, координация.
- Игорь: frontend обоих кабинетов и UX.
- Олег: архитектура, API, БД, workflow, adapters, Docker, CI и интеграция.
- Илья: чистый risk-модуль, словарь признаков, fixtures и эталонные результаты.
- Рамазан: независимая приёмка, E2E, коллекция запросов, отчёт о релизе; назначение подтвердить.

Общие схемы, миграции, статусы и Compose меняет владелец Олег по согласованию с затронутым исполнителем. Не редактировать чужую часть ради обхода контрактной ошибки.

## Неприкосновенные правила

- Веб-приложение, синтетические данные, автономный runtime, без платных API и корпоративных систем банка.
- Правила скоринга учебные. Не называть score вероятностью одобрения, не обещать SLA, точность и экономию без измерений.
- Все окончательные предложения/отказы в P0 подтверждает OFFICER; клиент отдельно принимает условия.
- Сервер проверяет роль и компанию для каждого объекта. UI скрывает лишнее, но не является механизмом авторизации.
- Состояние заявки хранится на сервере; изменения только через разрешённые команды state machine.
- Money = Decimal, JSON money = string. Missing не равен нулю. Техническая ошибка не равна кредитному отказу.
- Score отдельно от policy. Только одна реализация правил в risk-модуле, без сети и БД.
- Submit, решение, принятие и подпись идемпотентны. version, revision и run_id имеют разные значения.
- Запись состояния и audit атомарна. Устаревший worker не перезаписывает актуальные результаты.
- Demo mode обозначен явно; open demo session не считать production authentication.
- Реальная выдача, юридическая электронная подпись и внешние проверки не выполняются.
- Не сохранять настоящие секреты, данные клиентов и личные реплики из созвона. Не добавлять неоговорённые внешние сервисы.

## Code Simplifier

При написании и рефакторинге кода:

- Понятные имена вместо комментариев, поясняющих «что» делает код.
- Небольшие функции с одной ответственностью.
- Без дублирования и без ненужных абстракций «на будущее».
- Комментарии только о причинах решений (почему), не о пересказе очевидного.
- Рефакторинг сохраняет поведение; не менять контракты и тесты ради «красоты» без задачи.
- Предпочитать явный код скрытым магическим утилитам и premature frameworks.

## Frontend skills (Игорь / UI)

После чтения проекта и перед работой над `frontend/` или UX обязательно применить skills из `.agents/skills/`:

| Skill | Папка | Зачем |
|---|---|---|
| Impeccable | `impeccable` | дизайн/редизайн, иерархия, типографика, a11y, polish UI |
| Taste Skill | `design-taste-frontend` | анти-slop арт-дирекшн, премиальный look, не «типичный AI UI» |
| Motion React | `motion-react` | анимации на `motion/react`, reduced-motion, restraint в кабинете |

Правило Cursor: `.cursor/rules/frontend-skills.mdc` (срабатывает на `frontend/**`).  
Не подменять этими skills контракты API, статусы и risk-логику. Кабинет — режим Operate: ясность и консистентность важнее декора.

## Git и проверка

Работать в отдельной ветке, не делать force-push и не менять релизный тег. Перед merge запускать релевантные тесты и обновлять документацию. Нельзя менять expected теста только для сокрытия дефекта. Сброс данных разрешён только в явном тестовом окружении. Не переписывать код проекта целиком при локальном баге.

Завершая задачу, вернуть: изменённое поведение; файлы; фактически выполненные проверки и их результаты; известные ограничения; нужное действие следующего владельца. Непроведённую проверку обозначить как непроведённую. Заглушку обозначить как заглушку. Не заявлять готовность всего проекта по результату одной роли.
